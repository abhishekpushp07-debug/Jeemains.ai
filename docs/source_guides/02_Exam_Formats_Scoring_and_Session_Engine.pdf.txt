Master prompt: build the exam engine
VOLUME 02 / BUILDER INSTRUCTION

serving Tejas and a growing student population. Treat the following pages as executable

Build the shared core
Create one reusable attempt service with exam-specific policies for content structure, answer
types, navigation, timing, marking, and result release. Keep the scoring function independent of
React components. The server owns the accepted answer ledger, attempt deadline, paper lock,
and final score. The browser renders an accessible blue interface, stages edits, and sends explicit
commands. Display an independent-practice label wherever a student might mistake the platform
for an examination authority.
Implement the smallest complete path first: publish a reviewed paper, start an attempt, save
answers, recover a refresh, submit, calculate the score, and open the question-wise solutions.
Make this path work with actual database persistence before adding advanced analytics. Reuse the
approved content and solution contracts from Volume 03 and the measurement definitions from
Volume 04.
Preserve exam distinctions
Support the JEE Main Paper 1 integer-entry contract, the BITSAT optional extra-question lock, the
two WBJEE paper sessions with category scoring, and the COMEDK single-choice contract. WBJEE is
an OMR examination; label its online experience a digital adaptation rather than an official CBT
clone. Keep training conveniences, such as pause and hints, in a separate mode with a separate
comparison cohort.
Deliver concrete evidence
Return the policy registry, schema migrations, attempt and answer command APIs, deterministic
scoring fixtures, and runnable end-to-end checks. Provide an administrator preview that uses the
exact released configuration. Add a visible readiness report listing verified source documents,
unresolved rules, content review status, and failed checks. A paper with unresolved format or
scoring requirements must remain unpublished as an official-style simulator. Label comparative
scores Mock percentile within this paper's platform cohort. Never call them an NTA Score, official
normalized percentile, or official admission rank; this platform does not observe the authority's full
examination population.
ACCEPTANCE / PRECAUTIONS

POLICY GOVERNANCE
Make examination behavior data-driven. A school paper may be educationally useful without
matching an official examination format. Expose that distinction before the student starts,

Define the policy record
Create ExamPolicy fields for examCode, variantCode, examYear, policyVersion, status, sourceIds,
sourceDocumentHash, reviewedAt, reviewedBy, timingEvidenceStatus, and policyHash. Separate
machine-readable behavior from student-facing instructions. Support statuses draft,
evidence_pending, verified, approved, retired, and superseded. A verified source is not
automatically an approved software configuration; a reviewer must confirm that the configured
values correctly represent that source.
Use a field-level evidence ledger. Record which source supports duration, section counts, marking,
numeric input, navigation, review handling, accommodations, and disputed-question treatment.
Mark a missing field unresolved instead of filling it from a familiar prior year. When a notice
changes one field, preserve the old policy and create a new version with a precise diff.
Separate three product modes
Offer official-style simulation, digital adaptation, and custom training. Show a prominent mode
badge and describe departures in plain language. A custom integer-only JEE practice paper must
not silently inherit a full JEE Main claim. A compressed WBJEE session must not be presented as a
full two-paper rehearsal. Allow administrators to configure educational variants while keeping their
analytics cohorts distinct.
Prevent stale release claims
Do not infer 2027 rules from the retrieved 2026 bulletins. The release gate must require the
relevant official document or approved instructions for the selected year. Display the verification
date in the administrator report and a concise baseline year to students. For sources whose
publication date is not explicit, identify the document year and retrieval date without inventing an
issuance date. Treat active attempts as immutable consumers of their starting policy.
ACCEPTANCE / PRECAUTIONS
Changing a policy must never change an active attempt.
A missing timing source prevents the verified-simulator badge.

JEE numerical input and key precision
INTEGER ANSWERS
Implement integer entry as a distinct answer component. A numerical response must not
behave like a multiple-choice item or a calculator. Keep the student's raw input, validated
canonical value, and final committed value separate for debugging and question-wise review.
Build a deliberate input contract
Use an on-screen numeric keypad and a keyboard-accessible equivalent. Permit the characters
supported by the approved policy, including a leading minus sign when negative integer answers
are valid. Reject decimals, exponent notation, unit strings, multiple signs, infinity, and empty
sign-only values in the standard integer-entry variant. Make zero a valid value distinct from an
unanswered field. Show an inline error near the input without erasing the student's draft.
Normalize harmless formatting such as leading zeros only after preserving the original draft for
diagnostic purposes. Store the accepted integer as an exact decimal string or a suitably bounded
integer; never run arbitrary expressions supplied by the user. Avoid silently rounding a student's
decimal input into a scoreable response. The candidate performs the calculation; the platform
records the submitted integer.
Review mathematical keys
Keep an exact reviewed integer key and a separate authoring note containing the underlying
computed value where useful. The source requires nearest-integer rounding but does not fully
define a software tie-breaking function for every half-integer edge. Flag authoring keys that
depend on an exact half-integer convention for a subject expert. Do not use JavaScript rounding as
an unreviewed mathematical authority. [S2-01]
Test response semantics
Create fixtures for blank, zero, positive, negative, leading-zero, out-of-range, decimal, and
invalid-character drafts. Ensure Clear Response empties the editing field, and explicit save
commits the resulting blank under the selected navigation contract. In review, show the final
committed response and the key, with discarded drafts confined to an optional technical history.
Keep input length and domain constraints in the versioned policy so future variants can support
decimal answers deliberately.
ACCEPTANCE / PRECAUTIONS
Blank and zero produce different answer states.
A decimal draft cannot silently become an integer answer.
A reviewer must resolve a half-integer ambiguity before publication.

CHAPTER 05 / 25
JEE palette and review behavior
SAVE SEMANTICS
Reproduce the decision consequences of the published CBT instructions. The NTA appendix
says a palette jump does not save the current answer; Save & Next and Mark for Review &
Next save it. An answered-and-reviewed response is evaluated, while an empty reviewed
item is not. [S2-01]
Separate draft from committed response
Store draftAnswer in the editing and optional durable recovery context, never in the grading
ledger. A recovered draft is not a committed answer. Store committedAnswer in the accepted
ledger. Add visited and markedForReview as independent fields. An option click changes the draft.
Save & Next commits that draft, clears the review flag, and navigates. Mark for Review & Next
commits the current draft, sets review, and navigates. A palette or section jump follows the
policy's discard-draft navigation path. Preserve the previously committed answer when an unsaved
replacement is discarded.
Clear Response changes the editable draft to blank. The next explicit save commits blank. Verify
the final Clear Response behavior against the approved interface evidence before claiming exact
visual parity; include a visible unsaved-change indicator in the platform adaptation. Treat Save and
Mark actions as acknowledged commands, not mere changes of button color.
Render five understandable states
Derive not visited, visited without answer, answered, reviewed without answer, and answered plus
reviewed from accepted state. Pair each palette color with a shape or icon and readable legend.
The current question highlight is a separate visual layer. A pending save badge must not
masquerade as a confirmed answered state. Show consistent section counts derived from the
same accepted ledger used by submission.
Avoid accidental score changes
Do not score the review flag itself or add a penalty for revisiting. Keep a candidate's navigation
available within the permitted phase. In the submission summary, state which saved answers are
counted and how an empty reviewed question is treated. An optional training mode may autosave
on navigation, but it must declare that behavior and remain outside the official-style comparison
cohort.
ACCEPTANCE / PRECAUTIONS
Changing an answer and jumping away preserves the earlier committed answer.
An answered-and-reviewed correct response earns the same marks as a saved correct response.
The submission summary and palette use the same authoritative counts.

CHAPTER 07 / 25
BITSAT extra-question transaction
IRREVERSIBLE PHASE LOCK
Implement the extra phase as a guarded server transaction. Under the 2026 brochure, it is
optional only after all base questions are answered and time remains; accepting it prevents
returning to correct the original answers. The extra set has three questions each from
Physics, Chemistry, Mathematics, and Logical Reasoning. [S2-02]
Show an honest decision dialog
Offer a restrained button only when the server confirms eligibility. The dialog must say that the
base answers will be locked, the existing timer continues, and the extra phase retains negative
marking. Show accepted base completion and remaining server-derived time. Do not recommend
entering merely because the button is available. This choice is a strategy decision with a risk of
reducing the combined score.
Require a clear confirmation label such as Lock base answers and enter extras. Place Cancel with
equivalent readability. Disable repeated clicks while the request is pending. If the dialog is open at
expiry, show the final submission state; it must not grant a new phase or extra time.
Make the transition atomic
Process ENTER_EXTRA with an idempotency key, expected attempt revision, and latest accepted
command sequence. Lock the attempt, check every base item has a committed response, verify
the phase and deadline, freeze the base ledger hash, and transition once. Fetch extra content only
after authorization succeeds. Do not trust a browser-supplied completion count or unlock flag. A
retry returns the same accepted transition rather than making a second extra phase.
Preserve the locked contract
Reject all later base-answer edits server-side, including old queued commands from another tab.
Render locked base items read-only or remove their navigation during the phase. Keep the frozen
base answers available in the final review. Extras do not reset the attempt deadline. A refreshed
browser must recover the locked phase and remaining time. Track entry time and base snapshot
hash for diagnostics and later strategy analysis without inventing official extra-phase percentiles.
Preserve every untouched locked base contribution in the combined result, including its negative
marks; entering extras does not replace the base score.
ACCEPTANCE / PRECAUTIONS
A missing base response makes entry fail even if the browser claims full completion.
A queued base edit arriving after the lock is rejected.
Entering extras, refreshing, and retrying entry never unlocks the original paper.

Represent the two papers accurately

hours. The reviewed 2026 reference schedule is 11:00-13:00 for Mathematics and 14:00-16:00 for

CHAPTER 09 / 25
WBJEE categories and rational scoring
PARTIAL CREDIT ENGINE
Implement category-aware scoring from the official 2026 bulletin. Mathematics category
counts are 50, 15, and 10; Physics and Chemistry each use 30, five, and five. Keep category
on every item rather than deriving it from the display order. [S2-03]
Encode the scoring policies
Category 1 awards one for correct, minus 0.25 for incorrect; Category 2 awards two for correct,
minus 0.5 for incorrect. Both are single-correct, with a multiple-option response treated as
incorrect. Category 3 awards two for all correct options only; a proper correct subset receives two
times selected-correct count divided by total-correct count. Any incorrect option makes that
response worth zero; blank is zero. [S2-03]
Represent Category 3 keys and answers as option-ID sets. Score by set inclusion and cardinality,
not string equality of concatenated option letters. The same logical response must score identically
after any approved display permutation. Preserve the published option identities in the review view
so a source solution remains intelligible.
Preserve exact fractional totals
Use a rational numerator and denominator, or a documented high-precision decimal contract, for
intermediate partial credits. Do not round every item to two decimals before summing. A
two-thirds item and a four-thirds item must aggregate to two exactly. Define final display precision
separately from the comparison value. Include a short marks explanation in each question-wise
review, including the chosen set, correct set, and partial-credit calculation.
Validate potentially invalid responses
For the ordinary digital Category 1 and 2 view, use radio buttons and prevent multiple selection.
For imported OMR responses or an explicitly configured bubble simulator, retain malformed or
multiple-bubble responses and apply the appropriate category outcome. Category 3 uses
checkboxes and a label saying one or more answers may be correct. Never apply a generic
all-or-nothing checkbox score to a proper correct subset.
ACCEPTANCE / PRECAUTIONS
Key A,C with answer A earns one; answer A,B earns zero in Category 3.
The answer and key sets remain stable if visible option order changes.
Exact aggregate comparisons must not depend on two-decimal display rounding.

MODE HONESTY
The official WBJEE bulletin describes OMR response marking that cannot be changed or

Design the standard digital adaptation
Use an accessible question palette, paper timer, category badge, readable diagrams, and
appropriate single-choice or multi-select controls. Permit response revision until submission in the

interface supports editable responses unlike the physical OMR sheet. Do not advertise this

Keep category warnings near the options: the multi-select category has a different scoring rule,

Offer a separate irreversible-bubble mode

Compare like experiences
Persist the editing policy and OMR rehearsal flag with the attempt. Show the policy in the result
context and separate its analytics cohort from editable digital practice. Log changes and final fills

can revise a real OMR response. Provide a concise rehearsal note about checking question
numbering and avoiding rushed transfers, derived from observed errors rather than alarming
generic warnings.
ACCEPTANCE / PRECAUTIONS

REPRODUCIBLE RESULTS
Freeze the paper, policy, and presentation contract when an attempt starts. Every review

ALLOWED TRANSITIONS

a client-side score value.
Declare the states
Use CREATED, PREFLIGHT, READY, RUNNING_BASE, RUNNING_EXTRA, SUBMITTING, SUBMITTED,
SCORING, SCORED, RELEASED, and VOIDED. Allow CREATED to PREFLIGHT after authorization;
PREFLIGHT to READY after requirements pass; READY to RUNNING_BASE only through START.
START sets the authoritative start and deadline exactly once. RUNNING_BASE to RUNNING_EXTRA
is available only under the approved extra-phase policy. Either running state may close through
user submission or deadline expiry.
SUBMITTING freezes the response cutoff and gathers accepted records through the required
watermark. SUBMITTED contains the final immutable response snapshot. SCORING produces a
versioned score; SCORED awaits the configured result condition; RELEASED means the result is
eligible for display. Keep result_release_status and solution_release_status as independent server
gates. A raw score may appear while explanations remain pending under a solution embargo.
RELEASED never automatically grants solution access. VOIDED records a documented operational
or integrity decision with a reason, reviewer, timestamp, and audit reference; it must not mean
deleted.
Keep connectivity orthogonal
Do not make DISCONNECTED a lifecycle state that resets timing. Connectivity is an independent
client status: online, degraded, offline, reconnecting. A running attempt remains running during a
network loss. Likewise, focus, fullscreen status, current question, and writer-device ownership are
separate attributes. The state machine should remain understandable when multiple symptoms
occur at once.
Constrain transitions precisely
Require authorization, an idempotency key, expected revision, and policy guards for every
transition. A second START returns the existing attempt contract; it cannot create a later deadline.
A repeated SUBMIT returns the same final receipt. A request to reopen a submitted attempt fails
unless an authorized incident process creates a separate replacement or documented adjustment.
Recover a stuck SCORING operation with an idempotent retry; do not ask the student to retake the
paper because an analytics worker crashed.
ACCEPTANCE / PRECAUTIONS
Test every allowed transition and each forbidden adjacent transition.
Refresh never creates a new START or changes the deadline.
A scoring retry cannot duplicate the attempt or its final receipt.

AUTHORITATIVE ANSWERS
Implement a deterministic question reducer that derives status from data. Keep answer
content, visit history, review intention, local edit state, and network acknowledgement as
distinct concepts so the interface can explain every state accurately.
Define the stored fields
For each item, keep visited, committedAnswer, reviewFlag, questionRevision,
lastAcceptedCommandId, committedAt, and phaseLock. Keep draftAnswer, dirty, saveStatus, and
draftUpdatedAt in the editing context. Derive NOT_VISITED when never visited; VISITED_EMPTY
when visited with blank committed answer and no review; ANSWERED when committed answer
exists and no review; REVIEW_EMPTY when blank and reviewed; ANSWERED_REVIEW when
answered and reviewed. Zero and a nonempty option set count as answers.
VISIT marks visited without changing a response. SELECT replaces the draft for radio items or
updates the draft set for checkboxes. TYPE edits a numeric draft. CLEAR empties the draft. SAVE
commits the validated draft and removes review under the selected policy. MARK_REVIEW
commits the draft and sets review. JUMP discards an unsaved draft when the selected exam policy
requires that behavior. Explicitly define each event in code and documentation.
Validate every answer command
Check that the attempt is running, the writer lease is valid, the question belongs to this snapshot,
the phase permits editing, and the answer conforms to the type. Reject unknown option IDs,
duplicate IDs, out-of-domain numeric strings, and edits to locked base questions. Validation failure
must preserve the draft with a useful correction message. A stale revision returns the latest
accepted state and a conflict code rather than overwriting a newer answer.
Project state consistently
Derive palette icons, section counters, submission summaries, and review labels from the same
accepted fields. Overlay a pending-save marker without falsifying committed status. Emit compact
answer-history events for later change analysis, but score only the final accepted response.
Serialize state predictably so replaying the accepted commands reproduces the snapshot hash.
Avoid a separate UI-only answered boolean that can drift from the stored answer.

Replaying accepted commands reproduces the same final question state.
A pending save is visibly distinct from a committed answer.
A blank review state cannot accidentally become an attempted question.

Server clock, deadline, and timer
display
TIME IS A CONTRACT
Use one authoritative time contract per paper attempt. A browser countdown is a display of
that contract, not the mechanism that grants or removes time. The student must never gain
minutes by changing the device clock, refreshing, sleeping the phone, or opening another

Establish time once
At START, store serverStartedAt, approvedDurationSeconds, accommodationsAdjustmentSeconds,
and deadlineAt. For scheduled tests, explicitly define whether a hard close truncates late starts or
whether each admitted student receives the full duration. Show that rule before starting.

policy deliberately includes it. Starting an attempt must be a server transaction that returns the
existing record on retry.
Return serverNow and deadlineAt on start, resume, and heartbeat. Calculate an initial display
offset, then use a monotonic browser timer for smooth countdown between synchronizations.
Periodically reconcile with server time without letting the display jump backward into extra time.

late edits.
Do not pause on connectivity loss

page and offline banner. A pauseable training mode needs a separate elapsed-time model and a
different analytics cohort. Operator incident extensions, if enabled, require an authorized recorded
command with reason and new deadline; a client retry or support refresh is insufficient.
Define expiry and boundary behavior
Use a documented exclusive cutoff: a new answer command is eligible only when its trusted server
receipt time is before deadlineAt. Commands at or after the deadline are rejected as late. Align the
worker's closure query with the same inequality. Warn at configured thresholds through calm text
and an accessible optional sound. A warning is a product convenience, not permission to change
the examination duration.

Advance the client wall clock by a day; accepted remaining time stays unchanged.

Save queue and reconnection protocol
LOSS PREVENTION
Build a small durable client journal for the student's own responses and commands. It is a
recovery aid, not an authority that can override server deadlines or a substitute for
acknowledging that an answer was saved.
Specify the acknowledgement contract
Assign each answer command a UUID idempotency key, deviceId, writer fencing token, questionId,
expectedQuestionRevision, local sequence, and payload hash. Queue commands locally in order
and send them promptly. Return acceptedCommandId, serverReceiptAt, newQuestionRevision,
acceptedAnswer, reviewFlag, and attemptPhase. Display Saved only after this acknowledgement.
Show Saving, Offline: pending, or Save rejected when those states actually apply.
Use one authoritative writer lease per attempt. A second tab may observe state but must explicitly
take over the lease before editing; takeover invalidates the old fencing token. After takeover, the
old device's queued commands fail safely. Local sequence assists ordering within a device but
does not authorize a stale device or turn a client timestamp into trusted evidence.
Resume from the server snapshot
On reconnect, request lifecycle, phase, deadline, question revisions, and accepted command
identifiers. Deduplicate journal entries already acknowledged by the server. Replay remaining
commands only when the attempt is still running, their lease is valid, their target is unlocked, and
their revisions are compatible. Show an explicit conflict resolution screen when a later accepted
edit exists; do not silently prefer whichever request arrived last.
Handle practical network failures
Use bounded exponential backoff with jitter and retry only safe idempotent operations. Keep
pending response data across a refresh where storage is available, while clearing it after final
reconciliation under the retention policy. If storage is unavailable, warn before the attempt and
keep server saves frequent. Offline commands arriving after the strict cutoff are not scored, even if
the client claims they were made earlier. Explain that consequence calmly and preserve a support
trace without falsifying the result.
ACCEPTANCE / PRECAUTIONS
Lose the acknowledgement, retry, and receive the same accepted command result.
A second device cannot overwrite answers using an expired writer token.
Reconnecting after expiry shows rejected pending edits and the final receipt.

Submission and deadline race
resolution
EXACTLY ONE FINAL SNAPSHOT
Make submission a convergent server process. A student clicking Submit at the same
moment the deadline worker runs must produce one response snapshot, one completion
reason, and one receipt, regardless of request order or transport retries.
Define the ingress boundary
Record command receipt durably at a trusted server boundary and bind that timestamp to the
authenticated attempt. Do not use a client-supplied editedAt value for deadline eligibility. If
workers process requests asynchronously, eligibility may depend on this trusted receipt
timestamp, but finalization must wait for the pre-cutoff ingress watermark to drain. A command
merely sitting in the browser is not received.
For early submission, freeze a cutoff at the authorized submit transaction and ensure eligible
commands preceding that cutoff are resolved before the final response hash is calculated. The UI
should flush pending saves before asking for final confirmation. A user may choose to submit
despite a displayed save failure, but the dialog must state that only accepted responses will count.
Resolve competing closures
Acquire an attempt-level lock or equivalent compare-and-swap. If already closing or closed, return
its existing receipt. If time has expired, use deadline completion semantics even if the incoming
request says user submission. If still running and the early-submit policy allows closure, freeze the
user cutoff. Reject later answer mutations. Persist closure state and an outbox event atomically so
a worker crash cannot strand an unannounced successful submission.
Return an auditable receipt
Include attemptId, completionReason, cutoffAt, acceptedAnswerCount, rejectedPendingCount
where known, responseSnapshotHash, and resultStatus. Keep scoring separate from receipt
issuance; show Result processing if the score is not ready. Poll or subscribe using the existing
attempt, never create a new submission. The final score worker must use the frozen snapshot and
be idempotent by snapshot hash plus scorer and key versions.
ACCEPTANCE / PRECAUTIONS
Run submit and expiry concurrently in both orders; final responses match the declared cutoff.
A pre-cutoff acknowledged command cannot disappear from the score snapshot.
Duplicate submit requests return one receipt and one score run.
