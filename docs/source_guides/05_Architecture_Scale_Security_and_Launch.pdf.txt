Non-negotiable invariants and boundary
rules
MASTER.04 | CORRECTNESS BEFORE CAPACITY
Build these invariants into code, storage permissions, schema constraints and tests. They
define what must remain true when infrastructure is scaled, retried, restored or partially
unavailable.
Truth and examination invariants
A locked original, reviewed key, rule version or package manifest cannot be overwritten in place
by any application route.
One attempt binds one owner, home cell, immutable paper/configuration/key set, deadline
policy and current fenced writer.
A durably saved draft is separate from the committed response eligible for scoring. Background
autosave does not invent Save or Review events.
Only profile-eligible commitment events with trustworthy pre-deadline receipt may enter the
frozen submission.
Every acknowledgement states the actual durability level. A browser edit or volatile queue
acknowledgement is not a durable-answer receipt.
Question, subject and total marks reconcile using exact arithmetic; legacy results retain their
grading lineage.
Operational invariants
One idempotency scope plus key maps to one validated request body and one durable outcome. A
retry with a different body returns a conflict. A recovered writer accepts only the current fencing
generation. A revoked grant or changed base version cannot authorize a new protected mutation.
If audit, PIN validation or policy checks fail, protected source changes fail closed.
Signed candidate packages contain an allowlisted rendering projection only. Server key material
and unreleased solutions are separate artifacts with separate identities and permissions.
Authorization is checked before cached protected content is served. Admission uses reserved
capacity, while post-admission overload controls preserve the existing examination obligations.
Zero-loss statements are limited to the failure modes covered by the tested durable replication
policy. Asynchronous regional recovery may lose acknowledged facts within its measured
recovery-point window; it must trigger reconciliation and an explicit fairness process rather than
silently manufacturing missing answers.
ACCEPTANCE / PRECAUTIONS
Create a traceability row for each invariant: enforcing layer, failure scenario, expected result and
proof artifact.
Release is blocked by any source-bypass, wrong-score, cross-user access or covered-failure
answer-loss defect.

Shared names, mutation tiers and
deadline closure
MASTER.07 | CROSS-SECTION IMPLEMENTATION CONTRACT
Use consistent identifiers and action semantics across all sections. Compile one API schema
and one policy registry; do not create separate interpretations of immutable source,
commitment or release inside different services.
Canonical identifiers and mutation tiers
Use source_id and source_version_id for original document evidence; truth_version_id for the
reviewed locked interpretation; paper_version_id and exam_config_version_id for the attempt
manifest; package_id plus package_hash for delivery; key_version_id and grading_version_id for
scoring lineage; attempt_id, home_cell_id and writer_generation for live state. Item and Question
are naming aliases, not competing entities. All timestamps persist in UTC.
Classify mutations as ordinary owner data, editable editorial draft, protected truth successor,
protected activation/release, privileged account policy, or operational incident remedy. Ordinary
student response APIs never ask for the administrator PIN. Protected truth actions require a
payload-bound grant with actor, session, action, object, expected version, request hash, expiry and
single-use nonce. Privileged identity changes require their own independent administrator controls
and audit.
Trusted receipt and expiry closure
Distinguish browser action time, HTTP arrival, trusted cell admission time and transaction
completion. Use the reference protocol in the scale section: one fenced, attempt-scoped
transaction authority serializes authenticated command registration with deadline closure. Read
fresh authority time after admission serialization; for PostgreSQL use clock_timestamp() after the
lock, since now()/CURRENT_TIMESTAMP retain transaction-start time; register the full payload,
request hash, idempotency identity and next contiguous accepted sequence transactionally. A
mere pre-cutoff HTTP arrival is not acceptance. The close watermark contains only durably
committed accepted commands, and FINAL follows processing through that watermark.
Acknowledge accepted commitments under the configured synchronous local durability policy;
never silently degrade to asynchronous acknowledgement. Test a transaction admitted before
cutoff that finishes afterwards and races expiry. A late identical idempotent retry can recover its
durable outcome without changing the frozen answer. Alternative timing or durability policies
require a reviewed configuration and new proofs; they cannot vary silently across cells. An
overload rejection before durable registration remains a rejection; an unacknowledged local
response is not silently credited.
ACCEPTANCE / PRECAUTIONS
Demonstrate a pre-cutoff command whose processing finishes after cutoff under the selected
policy.
Race expiry, submit, lease takeover and retries; require one closed snapshot and one logical
result.
A transaction begun before cutoff but acquiring the attempt lock after cutoff is rejected.

Atomic admission: a permit becomes
one timed attempt
MASTER.10 | START LOGIC | RESERVATIONS AND CLOCKS
A waiting-room token is not an examination start. Bind admission to a qualified home cell and
turn a permitted reservation into exactly one durable attempt, with a reproducible start
receipt.
Issue a bounded, verifiable permit
An admission permit identifies the owner, cohort or assignment, paper/configuration versions,
home cell, allowed time window, activation generation, one reservation ID and signature. A client
cannot choose a different home cell or increase its priority. A valid permit also requires the
selected content and identity permissions. New admission uses a sufficiently fresh verified
activation decision; stale or unavailable admission authority can restrict new starts without
disrupting an already admitted attempt.
Consume and create in one transaction
In the home cell, verify the permit and current capacity, then atomically consume the reservation,
create the uniquely scoped attempt and start receipt, and move reserved capacity into the active
count. Use a durable idempotency record tied to the owner and request hash. A crash or lost
response must leave either a recoverable created attempt or an unconsumed reservation; it must
not create an uncounted attempt or charge two slots. The server returns the same attempt and
deadline on retry.
Set started_at and deadline_at through the pinned scheduling policy, which explicitly distinguishes
a common scheduled deadline from duration measured from an accepted individual start. Render
these returned facts on the client. Entering a waiting room, downloading a package or receiving a
permit must not start an individual attempt timer.
Release capacity without losing ownership
Reservation expiry releases only a reservation that was never consumed. It cannot free a slot
belonging to an active attempt. Close or cancellation releases active capacity once in the same
authoritative transition; repeated submit or expiry requests cannot decrement twice. A
reconciliation job compares counters with reservation and attempt ledgers and raises an alert
before unexplained drift is reused for admission. Browser disconnection or lease expiry alone does
not silently create a new attempt or reset time.
ACCEPTANCE / PRECAUTIONS
Race duplicate starts and simulate a crash at every reservation/attempt boundary.
A consumed permit retry recovers the original attempt even after permit expiry.
Start receipts, capacity counters and active attempt records reconcile exactly.

VAULT.02 | PROVENANCE / TRACEABILITY
Preserve the actual uploaded files before extraction, normalization, compression, or visual
cleanup. Store derived assets separately. A rendered crop or reconstructed equation may
improve delivery, but it cannot substitute for the evidence of what the uploader supplied.
Capture a defensible ingestion record

revised PDF.
Separate integrity from authenticity. A matching SHA-256 digest establishes that the checked
bytes match the recorded bytes; it does not prove who authored the paper, whether its claims are
correct, or whether the uploader owns publication rights. Record provenance assertions with their
evidence and reviewer status. Keep copyright and permission review distinct from the technical
hash check.
Tie each interpretation to evidence

decision. Link a key to its solution evidence and identify any disagreement between an answer list
and a worked solution. Store mathematical corrections as proposed interpretations with a reason,
never as edits to the original PDF. Require subject review before a conflicting key becomes
authoritative.

VAULT.03 | ADMIN AUTHORIZATION / BOOTSTRAP
Require a named privileged administrator authenticated through SSO and a strong enrolled
MFA factor before the PIN challenge. The PIN is a secondary authorization requirement; it
neither identifies a user nor replaces MFA, role checks, or review of a specific proposed
action.
Honor the owner value securely
Initialize the owner's required PIN as 5524 through a server deployment secret named
TRUTH_UNLOCK_PIN_BOOTSTRAP. Supply it through a secrets manager to the initialization service,
never a frontend literal, repository default, public environment variable, PDF upload, API log,
analytics event, or error message. Enroll a salted Argon2id verifier with a separately protected
pepper and record verifierVersion; restrict bootstrap-secret access to that service. Retain this
owner-selected value until an explicitly authorized rotation succeeds. The content vault must never
contain the plaintext PIN. [V-03]
Use the hashing library's documented Argon2id implementation and benchmark current
recommended work factors on the actual server. A short PIN has limited guessing entropy even
when hashed; the pepper, privileged identity, throttling, and scoped grant remain essential.
Protect secret transport with TLS and redact authentication request bodies before telemetry
interception.
Issue an operation-bound grant
Verify the PIN only after the policy service confirms eligibility. On success, issue a server-stored,
single-use grant bound to administrator ID, tenant, session, authentication assurance, resource ID,
action enum, parent version, proposed-diff hash, reason hash, and nonce. Recheck permissions
when consuming it. A proposed initial lifetime is 90 seconds; this is an operator-configurable
product default, not an external security standard. An altered diff, resource, or action requires a
fresh grant.
Throttle and fail closed
Use counters across administrator identity, tenant, and network signals, with safeguards against a

SCALE.08 | SCALE.08 | DURABILITY AND TIME
Implement a cell-local relational acceptance and seal protocol. HTTP arrival is not acceptance.
Preserve complete authenticated commands durably before acknowledging them, and make the
same fenced attempt authority serialize acceptance and closure.
Choose the durability contract explicitly
The selected reference acknowledges acceptance only after WAL flush on the primary and the
configured synchronous, failover-safe standby or quorum. Verify that the chosen offering implements
this durability contract; do not silently fall back to asynchronous acknowledgment when a standby
fails. Quorum loss triggers bounded backpressure or a retryable fail-closed response. RDS synchronous
standby and semisynchronous cluster offerings have distinct behavior [SCALE-S04, SCALE-S10].
Asynchronous cross-region replication has a separate nonzero loss window and regional RPO
[SCALE-S05]. Keep regional disaster guarantees separate from the synchronous local acknowledgment
contract. A timeout after transaction commit means outcome unknown to the client, not failure:
recover the durable receipt and outcome on a later idempotent retry.
Serialize complete acceptance with the close boundary
For each authenticated command, execute an attempt-scoped transaction using its row lock or
equivalent fenced compare-and-update. Recheck ownership, lease generation, profile and open state.
Assign acceptance time with PostgreSQL clock_timestamp() after acquiring that lock;
now()/CURRENT_TIMESTAMP retain transaction-start time [SCALE-S13]. A transaction started before
cutoff but locked afterward rejects; a command admitted before cutoff may finish afterward while close
waits. HTTP arrival and client time do not establish acceptance. Reject new commands at or after the
deadline. Append the full validated payload, payload hash, idempotency key, acceptance time and
next attempt-local sequence, and update last_accepted_seq in the same transaction.
Allocate no accepted sequence outside that transaction: rollback removes both append and counter
advancement, preventing allocated-but-unwritten holes. The close operation uses the same attempt
authority and transaction boundary; it stops acceptance and captures a watermark containing only
committed accepted commands. Finalization drains and applies every contiguous accepted sequence
through that watermark before entering FINAL. Delayed processing adds no answering time. Store final
receipt and outcome durably; an identical late retry recovers them without accepting a new command.
Partition authority by stable home cell and attempt; require no global write lock.
Fence an old writer before promotion and prevent dual acceptance authorities.
Separate draft persistence from eligible scored-commitment commands.
Bound processing queues and preserve every already accepted full command.
ACCEPTANCE / PRECAUTIONS
Crash between append and counter update: require complete rollback or complete durable
acceptance.
Race closure, quorum loss and late retries; FINAL must include exactly the sealed accepted sequence
set.
Start before cutoff, acquire the serialized lock after cutoff: require rejection.

OPS.08 | OPERATIONS / RPO, RTO AND RESTORE VALIDATION
Define recovery point objective as allowable data loss and recovery time objective as restoration

regional-disaster RPO <= 5 minutes with RTO <= 60 minutes. These are acceptance targets, not
vendor guarantees.
Disclose the regional loss boundary
Asynchronous cross-region replication can lose recently acknowledged data during unplanned failover;
AWS explicitly describes this risk for Aurora Global Database [OPS-S07]. Measure actual replication lag
and the last verified durable watermark. Do not restate the five-minute regional RPO as zero loss. A
recovered response store must expose which attempts fall in a potentially missing interval.
Before promotion, establish one globally exclusive writer epoch or independently verified fencing of the
old region's ingress and writer. If neither can be proved, remain unavailable rather than allow split-brain
writes. Bind attempt routing and leases to the promoted epoch. Reconcile pre-deadline ingress ledgers

accepted answers.

versions, incident exceptions, cohort eligibility snapshots and audit references. Protect independent
backup vault access and recovery credentials. Validate encryption-key availability, KMS permissions,
network configuration, database engine compatibility and immutable image/package access in the
recovery environment. A backup status of completed does not prove decryptable or usable application
recovery.

validation workflows and requires relevant key access [OPS-S08, OPS-S09]. Restore to an isolated
environment, verify package hashes, row counts, sequence bounds and receipt-to-response reconciliation,

embargoed content exposure.
