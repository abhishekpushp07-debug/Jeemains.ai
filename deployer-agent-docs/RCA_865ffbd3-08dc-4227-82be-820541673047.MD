# RCA — /api/sets/{id}/preflight stuck on "Checking…" (jeelive.ai)

## Problem statement
A signed-in student on mobile Chrome opened `/sets/2cef7d00-a0…` and pressed **"Check my device"**. The button stayed on "Checking…" for >2 minutes (screenshot ~02:15 IST / **20:45 UTC 2026-11-16**, shortly after the 20:03 UTC deploy, run `865ffbd3-08dc-4227-82be-820541673047`). Frontend calls `POST /api/sets/{id}/preflight` with `{preview:false, test_response:"55"}`.

## The set in question
Resolved from prod Mongo (`tejas_sets`, id `2cef7d00-a0b1-5af0-a8b1-6272e32d1c0f`):
- **title:** "Mock 1"  | **test_kind:** `mock` (NON-PYQ → the `validate_refs` path, not the PYQ threadpool path)
- **series_id:** `all-india-jee-2026-27`  | **book_import_id:** `80c48d77-2bb0-5443-9c18-7458f226e25b`
- **revision:** 6  | `full_length: true`
- **questions:** **75** (25 Mathematics + 25 Physics + 25 Chemistry)
- Each question carries 1 `q_ref` + 1 `s_ref`, each pointing at a distinct private-storage `file_id` → **~150 unique crop refs** over ~150 source PDFs (`file_ids` array ≈ 150 entries).

## What the logs show
- Backend logged **exactly ONE** preflight for this set in the last 24h:
  `POST /api/sets/2cef7d00-a0b1-5af0-a8b1-6272e32d1c0f/preflight HTTP/1.1" 200 OK` — i.e. the request **did eventually return 200** server-side.
- `tejas_preflight` doc for this user/set was written at `at = 1794861852.114` = **20:44:12 UTC (02:14:12 IST)** — matches the screenshot time, confirming the request **completed and persisted**, it did not error.
- **No** object-storage, threadpool, timeout, or 5xx error lines anywhere in the run's logs (searched `timeout|timed out|TimeoutError|storage|threadpool|validate_*|crop`). Nothing failed — it was slow, not broken.
- Pods healthy the whole window: both replicas `Running`, `restart_count:0`, no OOMKilled/CrashLoop/evict (the FailedScheduling warnings are 20:01 UTC rollout noise only). So this was NOT a resource kill. Tier is Elite (2 CPU / 8Gi, 2 replicas) — not the constraint.

## Root cause (code performance — confirmed by reading source in an eph sandbox)
`backend/tejas/attempts.py::preflight` → `validate_sources(s, entry.refs)`. For a non-PYQ set it takes the ELSE branch and calls `content.py::validate_refs`, passing **all ~150 unique refs as `q_refs`**. `validate_refs` does:

```python
for key in ["q_refs", "s_refs"]:
    for r in q.get(key, []):            # ~150 refs
        if r["file_id"] not in source_map:
            source_map[r["file_id"]] = await get(files, r["file_id"])   # mongo meta (memoized)
        f = source_map[r["file_id"]]
        await run_in_threadpool(render_crop, f, r, 0.3)   # <-- AWAITED ONE REF AT A TIME
```

`render_crop` (`derivatives.py`) on a cold cache (first preflight, or after the per-minute `needs_check` window / any file-list change) does, per ref: `get_object(source['path'])` = **download the full source PDF from private object storage**, `sha256` the whole blob for integrity, then `_render_crop_png(...)`. Its PNG `ByteCache` is keyed per-ref, so every one of the ~150 distinct refs is a cache MISS → ~150 cold PDF downloads + renders.

**The loop `await`s each `run_in_threadpool(...)` sequentially — there is no `asyncio.gather`/concurrency and no dedup of `get_object` across refs.** So preflight performs **~150 sequential (object-storage fetch + sha256 + PDF render)** operations on the request thread. Even at a few hundred ms each this runs well past a minute — which is exactly what the single observed call did (started ~20:4x, persisted at 20:44:12 UTC).

(The PYQ branch `validate_source_crops` is also awaited sequentially but groups refs by file_id and has a validation cache, so it does far fewer fetches. This set is `mock`, so it hit the heavier per-crop path.)

## Why the user saw "Checking…" forever while the backend logged 200
The frontend is served via **Cloudflare** (worker → k8s backend). Cloudflare's origin timeout is ~100s (edge returns 524). A preflight that takes ~2 min exceeds that: the browser `fetch` is cut off / hangs so the UI stays "Checking…", while the backend thread keeps grinding, finishes, writes `tejas_preflight`, and logs `200 OK`. NOTE: the 499/504/520/524 you asked about are **edge/ingress** statuses — they are generated by Cloudflare, NOT by uvicorn, so they do not appear in backend logs (which only show the eventual 200). I could not read the edge status directly.

## Latency distribution over last 24h — NOT COMPUTABLE
Two hard limits:
1. The app emits only uvicorn access lines, which carry **no latency field**, and there is no app-level timing instrumentation for preflight.
2. Backend logs contain **only one** `/api/sets/*/preflight` request in the whole 24h window (this incident) — a single sample, so there is no distribution to report. (`/preflight` is a low-traffic, per-attempt action.)

## Scope of verification
Diagnosis is from prod logs + prod Mongo + reading the shipped source in an eph sandbox. I did **NOT** reproduce the latency end-to-end — the sandbox has no app secrets, no private object storage, and no real source PDFs, so the ~150-fetch cost cannot be exercised there. The code path and the ref fan-out are confirmed; the exact per-request wall-clock was inferred from the persisted `tejas_preflight` timestamp, not measured.

## Suggested fixes
1. **Code (E1)** — Make source validation concurrent and dedup storage reads so preflight finishes inside the edge timeout:
   - Replace the sequential `await run_in_threadpool(render_crop, ...)` loop in `validate_refs` with bounded concurrency (`asyncio.gather` + a `Semaphore`, e.g. 8–16) across the ~150 refs.
   - Dedup `get_object(source['path'])` per `file_id` (fetch each source PDF once, render all its crops from the in-memory bytes) instead of re-downloading per ref.
   - Consider doing the full-source verification off the request path (background / cached by revision) so "Check my device" only confirms connectivity + the test response, or raise the preflight timeout handling.
2. **User (test_and_verify)** — To confirm the client-visible mechanism I could not read from the edge: reproduce on the set and capture the `/preflight` request in Chrome DevTools (Network) / Cloudflare analytics and confirm it is a ~100s **524** (edge timeout), not a backend 5xx.
