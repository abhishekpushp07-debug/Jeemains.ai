# RCA — jeelive.ai (campus-search-debug): AITS 33 MB PDF upload "stopped / showed an error"

**Mode:** READ-ONLY diagnosis. No deploy, restart, secret/env change, or DB write was performed.
**Active run:** c64e826b-15e4-4b18-a60b-5ccfb454ec52 · tier_4 · frontend_type=cloudflare · cluster deployment-cluster-06
**App health:** Live and serving (hundreds of 200s in the window). Pods: 2 Running, restart_count=0, no OOM, kill_findings=[]. This was a single failed upload attempt, not an outage.

## One-line problem statement
Owner uploaded the ~31.5 MB "AITS" PDF (JEE_Main_2027_Full_Book_Mocks_01-50.pdf) from Master upload after today's deploy; it errored mid-transfer. Error text was not captured by the owner.

## How the upload works (from source — backend/tejas/book_imports.py, backend/tejas/book_store.py, frontend/src/components/master/uploadBook.js)
Chunked upload, NOT a single large POST:
1. `POST /api/admin/books` — creates the book (state=`uploading`), returns `chunk_size` and `received_parts`. CHUNK = 512*1024 = 524288 bytes.
2. `PUT /api/admin/books/{id}/parts/{n}` (Content-Type application/octet-stream) — one request per 512 KB chunk. Server validates per-part size, sha256, 30 s receive timeout.
3. `POST /api/admin/books/{id}/complete` — requires `parts_count == ceil(size/CHUNK)`, then flips `uploading → received` and calls `dispatch()` → enqueues the `book_step` job that reads the PDF.
Frontend loop retries each part up to 4× on network-error / 5xx / 408 / 429; after 4 failures it throws: **"Sending stopped. Choose the same PDF again; parts already sent are kept."** `/complete` runs only after all parts succeed.

## Evidence
### The failing object (prod DB, read-only)
`tejas_books` — three copies of the SAME file (size 31,553,998 bytes, dest `jee-main:aits`), i.e. the owner uploaded it 3 times:
- `7f045c92…` (Nov-14 ~22:45Z) — state `attention_needed`, pages 4481 / read 4481 → processed OK (before today's deploy).
- `05f7a301…` (Nov-15 ~14:58Z, before the 22:03Z deploy) — state `attention_needed`, 4481/4481 → processed OK.
- **`80c48d77-2bb0-5443-9c18-7458f226e25b` (Nov-16 ~06:45Z, AFTER the 22:03Z deploy) — state `uploading`, no pages, no job.** archived_at ≈ 353 s after create (owner dismissed it ~6 min in). filename JEE_Main_2027_Full_Book_Mocks_01-50.pdf, sha256 recorded, rights_confirmed=true.

### Parts math
ceil(31,553,998 / 524288) = **61 parts expected (indices 0–60)**.
`tejas_book_parts` for 80c48d77: **count=40, distinct numbers = 0–39 contiguous** → upload stalled at **part index 40 (41st chunk)**; 21 parts never sent.

### Request log (run c64e826b, last 24 h)
Point 1 — PDF upload requests for 80c48d77: `POST /api/admin/books` → **200**; `PUT …/parts/0…39` → **all 200** (part 38 appears twice, from two Cloudflare edge IPs = a retried chunk that then succeeded). Then `POST …/dismiss` → 200 (the archive).
- **No request for part 40 (or any of 40–60) ever reached the backend.** No `POST …/complete` ever reached the backend.

Point 2 — No backend tracebacks/warnings. No pymupdf/fitz/memory errors. Only normal uvicorn starts (deploy pod 22:01Z + autoscale replica 02:36Z). No OOM, no restarts, no evictions (get_pod_events).

Point 3 — `tejas_jobs`: latest book jobs are all for 05f7a301 / 7f045c92 and status `done`, error:"". **No job of any kind exists for 80c48d77** (because `/complete`/dispatch never ran). No `status:failed` book jobs. `tejas_book_allowances` empty — no quota/allowance gate involved.

Point 4 — Edge/ingress body limit: NOT implicated. The app deliberately chunks to 512 KB per request precisely to stay far below edge limits; Cloudflare's ~100 MB body cap and the app's own 100 MB limit (LIMIT in uploadBook.js / listing endpoint) are irrelevant to a 512 KB part, and 31.5 MB < 100 MB. No 413 anywhere. Parts 0–39 (same size, same route, same edge) passed cleanly.

## Root cause
The transfer of **part index 40** (a 512 KB chunk) failed on all 4 client retries, so the browser aborted the upload with "Sending stopped…" and never called `/complete`; the book therefore stayed in `state:"uploading"` with 40/61 parts and no processing job, and the owner then dismissed (archived) it. Because the backend logged **no part-40 request and no 408/413/429/5xx**, that chunk's PUT never reached the origin — it failed at or above the Cloudflare edge (connection drop / origin timeout / reset between the owner's browser and the edge/origin). The flakiness is visible even in the successful run (part 38 needed a retry across two edge IPs); part 40 simply exhausted the 4 retries.

This is a transient transport failure during a long 61-request upload — **not an application-code fault** (backend accepted every part it received and would have accepted the rest) and **not a reproducible platform/edge body-size limit**. It cannot be attributed to a specific Cloudflare defect vs. the owner's own network from the logs alone; both present identically (request never reaches origin, no backend log). The "started after the latest deploy" timing is coincidental — the current build accepted 40 parts without error, and nothing in the upload code path is implicated by the deploy.

## Recommended fixes
1. **User — retry the upload, ideally on a stable/wired connection.** It was a dropped chunk, not a size limit or a server error. Note: the failed attempt was dismissed/archived, so its 40 saved parts will NOT resume — `create()` routes an archived duplicate to a fresh book id, so a new upload re-sends all 61 chunks from scratch. If it fails again mid-transfer, note the exact part number shown and whether it recurs across different networks.
2. **Code (optional hardening, E1) — make the uploader more resilient / resumable.** `frontend/src/components/master/uploadBook.js` retries only 4× per part and, after a dismiss, cannot resume the partial (new book id). Options: more retries / longer backoff, auto-resume on transient drops, and let a re-selected PDF resume an archived/dismissed partial via its `received_parts`. This reduces recurrence but is an enhancement, not the root cause. Not reproducible in the sandbox (requires the live edge/network path; no app secrets/edge available there).
