## ROOT CAUSE (proven)
The production page reader (`book_reader.py`, READER_VERSION 5) **never classifies the detailed-solution pages as `solution`/`key`** for these AITS PDFs, so every solution page is treated as another question page. The single mis-classification cascades into ~500 blockages per mock.

Mechanism, by code line:
- `ROLE` regex (line 8) is matched with **`ROLE.fullmatch(value)`** (line 171) and only emits a page `role='solution'` header when the whole line is the role label (optionally qualified by subject/test). In these PDFs the solution header is a **composite running header** — `"MATHEMATICS / DETAILED SOLUTION"` (plus a per-page footer index `"INDEX QUESTIONS ANSWER KEY SOLUTION"`). Because of the `"MATHEMATICS / "` prefix, `ROLE.fullmatch` fails, so **no `role='solution'` header is added** (line 177).
- With no solution-role header, `page_role` falls back to the carried `context.get('role')` which is still `'question'` (line 252), so solution-page regions are emitted with `role='question'` (line 378).
- On those pages a printed answer exists (`Answer: (A)`), so line 388 fires `"Answer visible near QN; separate it from the question crop."` and the answer leaks in as `region.answer="A"`; the folded-in pages also inflate Mock 1 to 150 "questions" → line 150 of `book_publish.py` fires `"Printed question count conflicts with the proposed count…"`.
- Because no page is ever `solutions`/`key`, `book_publish.py` finds empty `solutions`/`keys` for every question and emits (lines 177/181/189/190) `missing or conflicting supplied key`, `response type is unresolved`, `original solution expected but not captured`, `original key region required`, and sets `solution_kind='answer_key_only'` (line 197). Several of these are in the HARD set (line 16), which is why mocks stay `state:"held"` / book `attention_needed`.
- Secondary: the QUESTION-page crop captured only the thin title strip (rect height ≈0.023) and did not attach the on-page subject ("MATHEMATICS") to the region, so `subject`/`response_type` stay empty → the three question-page issues on pages 5–79 (lines 389, 393–394).

This is a **source/code** defect (the reader's section-header detection), not a secrets/infra/tier/DB-data problem. The deploy pipeline is healthy and the app is live.

## SUGGESTED FIX (hand to E1 — do NOT auto-apply)
Primary — `backend/tejas/book_reader.py`:
1. Detect the solutions/answer-key section even when the role label is embedded in a composite running header or page footer. Replace the `ROLE.fullmatch(value)` gate (line 171/177) with a search that recognises `DETAILED SOLUTION(S)` / `SOLUTION(S)` / `ANSWER KEY` appearing as a running header segment (e.g. after `"<SUBJECT> / "`), and/or treat the repeated footer index token `SOLUTION` on a page as a role signal. Once detected, set `page_role='solution'` so solution pages classify as `solutions` and attach `role='solution'` regions.
2. Guard the question-page crop so the region spans the full question body + options (not just the title line), and attach the page's subject header to the question region so `subject`/`response_type` resolve.
Downstream — `backend/tejas/book_publish.py` only emits the per-question HARD issues as a *consequence* of (1); it should need no change once solution/key pages are classified, but verify `solution_kind` becomes `supplied_worked` and the HARD-set issues clear after the reader fix.
