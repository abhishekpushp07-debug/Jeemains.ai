# RCA — JEELIVE.AI "new picture answers not live"

## Scope
Read-only investigation. No redeploy, no secret change. Deployment `campus-search-debug` (04241398-cdb1-4ca5-8232-874011d24cc3), live at https://jeelive.ai (Cloudflare frontend + FastAPI backend, tier_4).

## Verdict
**The production deployment is correct and healthy. The new picture-answers code and config ARE live on the backend.** No deployment-, build-, secret- or log-level problem was found. If the partner still sees the old answers, the cause is downstream of the deployment (client/CDN cache or test method), not the serving build.

## Evidence

### 1. Latest deploy succeeded and is the one serving traffic
`describe_deployment_state` recent_runs, both of today's deploys succeeded:
- **Active run `15dbf4ec-8f66-4111-ab0e-498613f741c4`** — type=redeploy, created **2026-11-23T17:18:02Z**, completed **17:24:07Z**, status **success**. This is `active_run_id` → it is the run currently serving jeelive.ai. Image `customers-app-4@sha256:fc05cc7...3c67`.
- Earlier run `b3658c8d...` — type=replacement, 17:04:02Z → 17:10:11Z, success (the ~17:05 deploy).

The 17:18 redeploy pulled source AFTER commit 14b2b76 (17:12:59Z), so it captured that commit.

### 2. The live build contains the 14b2b76 change (default '*')
Read the active run's pulled source in an eph sandbox. `backend/tejas/pictures.py` line 12 is exactly:
```
_setting = os.environ.get('PICTURE_PILOT_PHONES', '*').strip()
EVERYONE = _setting == '*'
```
Module docstring: "On for every student by default." → confirms the new default `'*'` (picture answers for every student) is the code that was built and deployed. The old `'7004186276'` default only appears in `backend/tests/pictures_iso220.py` as a per-test override, not in the live module.
(Note: source archive excludes `.git`, so the commit SHA cannot be read directly — but the file CONTENT matches commit 14b2b76's change byte-for-byte, so 14b2b76-or-later is in the live build.)

### 3. No PICTURE_PILOT_PHONES secret exists in production
`list_secrets` on the active run — the full key list does NOT contain `PICTURE_PILOT_PHONES`. So nothing overrides the `'*'` default; `EVERYONE` evaluates True → feature enabled for all students. (Keys present: ADMIN_EMAIL, ADMIN_PASSWORD, CORS_ORIGINS, DB_NAME, EMERGENT_LLM_KEY, ENABLE_HEALTH_CHECK, FRONTEND_URL, INTEGRATION_PROXY_URL, JEELIVE_APP_API, JEELIVE_SITE_URL, JWT_SECRET, MEDIA_CDN_URL [empty], MONGO_URL, REACT_APP_BACKEND_URL, SUPABASE_SECRET_KEY, SUPABASE_URL, WDS_SOCKET_PORT, WEBHOOK_CRON_SECRET.)

### 4. pyoxipng 9.0.1 installed in the build
`requirements.txt` line 122 pins `pyoxipng==9.0.1`. Build `15dbf4ec` build_state=**SUCCEEDED**; the pip "Successfully installed …" line includes pyoxipng (matched on grep) and pip exited clean with no resolution error.

### 5. No picture/media/asset errors in production logs
`fetch_app_logs` since 17:00 UTC (1440-min window, filter pictures|media|asset|traceback|500|Error|Exception) returned only transient boot-time noise: one `connect() failed (111: Connection refused)` to the backend at 17:23:41 and two `GET /health 404` during startup — normal rollout warmup. **No 5xx and no tracebacks** from `tejas/pictures.py`, `tejas/media.py`, or the `/api/attempts/.../asset`, `/assets/links`, `/assets/pack` routes.

## Conclusion
Everything under the deployment pipeline's control is correct: the right commit content is live, the default is `'*'`, no override secret exists, the dependency installed, and the app serves with no related errors. The feature is live backend-side. The "not live" report points to something the deployment cannot see — most likely a stale cached frontend bundle / CDN cache, or the check was done without a fresh logged-in student session. Recommend verifying via a hard-refresh / incognito logged-in student session and capturing the actual failing request + status if it persists.
