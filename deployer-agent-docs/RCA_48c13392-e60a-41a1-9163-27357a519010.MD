## One-line problem statement
A ~49.1 MB PDF (`mathematics chapterwise`) sits in state `received`, "Supabase mein 0% · 0 KB / 49.1 MB", "waiting for Supabase" for ~hundreds of minutes, while the storage health badge is GREEN — and other books stop by themselves too.

---

## ROOT CAUSE (verified)
The Supabase **resumable (TUS) PATCH returns HTTP 409 at byte offset 0 on every attempt**. In `backend/tejas_storage.py`, `_tus()` treats 409 as **retriable** (line 251: `if misses > 5 or (r is not None and r.status_code not in TRANSIENT + (409,))`). So it retries the 6-MB PATCH 6 times, all 409, then raises:

> `Supabase big-file upload stopped at 0 of 51535181 bytes (409).`

`put_object()` catches that, calls `_strike()` and re-raises it as **`StorageWaiting`** — i.e. "Supabase is temporarily down, wait and auto-resume." The `book_step` job therefore reschedules **forever** (85 `storage_waits` so far) and the book never leaves `received`.

Meanwhile the health probe writes a *tiny* file with a single `POST ... x-upsert:true` (`sb_put` small-file path), which **succeeds** and calls `_ok()` — resetting the down-state. That is exactly why the **badge stays green (Supabase 1698 ms) while the 49 MB file is permanently stuck at 0%**. The big-file TUS path and the small-file health path hit different Supabase behaviours.

The 409 itself is a **persistent conflict** for this object key, NOT a transient outage — waiting cannot clear it. It is mis-classified as transient, which is the core defect.

Contributing code factors:
- `x-upsert: 'true'` is sent only on the TUS **POST create** (line 231), never on the PATCH/finalize — so an already-existing object or a stale/locked resumable session for the same key yields 409 that upsert never resolves.
- `_carry_on()` re-adopts the stored `payload.transfer.url` for up to `RESUME_SECONDS = 72000s` (20h). The stuck session (~400 min old) is still inside that window, so each retry can re-attach to the same poisoned upload URL instead of starting fresh.

Not reproduced in sandbox: the eph pod has the source but **no Supabase credentials**, so the live 409 cannot be exercised there. Verified: the 409 status in logs + the exact code path. Inferred: the specific Supabase-side conflict cause (existing object / stale resumable session).

## SUGGESTED FIXES

### A. Code (E1) — primary fix, requires redeploy
In `backend/tejas_storage.py` `_tus()`:
1. **Remove 409 from the retriable set** (line 251). A 409 on the resumable PATCH is a persistent conflict, not a transient outage — it must not become `StorageWaiting`.
2. On 409, **recover instead of looping**: `DELETE` the existing object / abandon the stale resumable session for that key, then create a fresh TUS upload (the POST already sends `x-upsert:true`); if it still 409s, raise a permanent, actionable error (like `SupabaseRefused`) so the book stops with a clear reason rather than waiting forever.
3. **Clear `payload.transfer` on a 409** so `_carry_on()` cannot re-adopt the poisoned upload URL within the 20h `RESUME_SECONDS` window.
4. (Optional) Carry `x-upsert`/overwrite intent onto the finalize path, and separate "big-file upload broken" from "Supabase down" so the health badge reflects big-file failures.

### B. Immediate unblock (Supabase dashboard — user/third-party)
Delete the leftover/partial object and any in-progress resumable upload for key `jeelive/books/4e23420a-ebf4-5a84-a12b-939e8b9ed3c3/original.pdf` in bucket `jeelive-jeelive-ai`, then re-upload the PDF. This is the exact destination returning 409. (Could not verify the object state from here — no Supabase access.)

### Explicitly ruled out
Not memory/OOM (0 restarts, 16Gi limit). Not a secret/env issue. Not a DB duplicate or prior delete. Not the small-file/health path (that works). The defect is the big-file TUS 409 handling.
