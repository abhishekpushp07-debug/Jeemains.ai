## ROOT CAUSE (confirmed)
`backend/server.py`:
```python
origins = [os.environ["FRONTEND_URL"].rstrip("/")]          # allowlist = EXACTLY ONE origin
app.add_middleware(CORSMiddleware, allow_origins=origins, allow_credentials=True,
                   allow_methods=["GET","POST","PUT","PATCH","DELETE"], allow_headers=["Content-Type"])
@app.middleware("http")   # write fence
... if request.method in ["POST","PUT","PATCH","DELETE"] and origin and origin not in origins:
        return error_response("Cross-origin write rejected.", 403, "origin_denied")
```
Both CORS and the write-fence key ONLY off `FRONTEND_URL`. Browsers send an `Origin` header even on SAME-ORIGIN POSTs, so because `FRONTEND_URL != https://jeelive.ai`, the fence rejects the login POST with 403 even though the request is same-origin (jeelive.ai page → jeelive.ai/api). CORS preflight for other origins (www, default host) likewise 400s — earlier run fd8894b5 logged `OPTIONS /api/auth/session 400`, `/api/auth/phone 400`, `/api/series 400` from Cloudflare IPs. So the single wrong `FRONTEND_URL` breaks login on every hostname.

## FIXES (no redeploy/secret/data change performed)
1. **User — Secrets:** Set `FRONTEND_URL` to the exact canonical origin, byte-for-byte, no trailing slash — `https://jeelive.ai` (since www redirects to apex, apex is the canonical origin the Origin header carries). Then redeploy. Clears the 403 write-fence + CORS preflight. `CORS_ORIGINS` has no effect.
2. **Code — E1 (robust fix, no CSRF weakening):** The single-origin allowlist is the flaw — one app served on apex + www + default host but only ONE origin trusted. Change `server.py` to build `origins` from a LIST of trusted hostnames (parse the existing `CORS_ORIGINS` as comma-separated, or hardcode the known prod hosts: https://jeelive.ai, https://www.jeelive.ai, https://campus-search-debug.emergent.host) and apply that same list to the write-fence. This keeps the cross-origin write protection (CSRF defense) intact while trusting all real app origins.
3. **User — Domain:** Let www.jeelive.ai's Cloudflare cert finish issuing (currently "initializing") to fix the slow first load on www; DNS is already correct.
