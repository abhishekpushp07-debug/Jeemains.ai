# RCA — jeelive.ai: Super Admin PDF upload fails + slow (2026-11-21)

## Summary
The Super Admin "upload PDF / book publish" flow fails because the **Emergent private object-storage integration returns HTTP 500** when the book-publish worker writes crop images. The app surfaces this as `tejas_storage.StorageError: Private storage unavailable (500)` and marks the book `state=failed`. This is a **platform/account storage-service issue** ("check account storage permissions and quota"), **not** the app's code, a missing secret, the tier, or an ingress size/timeout limit.

- It is **NOT** caused by today's redeploy. The identical StorageError (500) was already occurring on the **previous run `faab460a`** (deployed 2026-11-20 19:47 UTC) for *different* books (`3a704ed9`, `4e23420a`). It predates the 15:00–16:00 UTC redeploy.

## Root cause
The Emergent private object-storage service (`INTEGRATION_PROXY_URL` → `/objstore/api/v1/storage`, authenticated with `EMERGENT_LLM_KEY`) returns **HTTP 500 on object PUT**. `tejas_storage.request()` retries connection errors and 503s but surfaces 500 immediately as `StorageError`. The book-publish worker can't write crop images, so every publish/upload fails and the book is marked `failed`. The failure is **persistent across runs and books**, so it is a platform/account storage condition — the error text itself points at **storage permissions/quota**.

Secrets checked (active run): `EMERGENT_LLM_KEY`, `INTEGRATION_PROXY_URL`, `MONGO_URL`, `DB_NAME` all present/non-empty (`MEDIA_CDN_URL` is empty but unrelated). So this is not a missing-secret case.

## Not the cause (ruled out with evidence)
- App source bug — code handles storage failures cleanly; traceback is a clean surfaced error, not a logic bug.
- Today's redeploy — storage 500 pre-existed on prior run `faab460a`.
- Cutter version 2→3 — still 2.
- Tier / OOM — pods healthy, 0 restarts, no OOM.
- Ingress 413 / timeout — none observed; limits are generous.

## Suggested fixes
1. **Platform (Emergent):** Investigate the `/objstore` storage service returning HTTP 500 for this deployment's account — check the storage account bound to this app's `EMERGENT_LLM_KEY` for quota exhaustion, permission/binding breakage, or a service-side 500. This is the blocking issue.
2. **User:** Open an Emergent support ticket quoting deployment_id `04241398-cdb1-4ca5-8232-874011d24cc3` and the active run `bc239ca9-...`, and verify private-storage quota/permissions on the account (the error explicitly says "check account storage permissions and quota"). Once storage is restored, re-run the failed book (`eed94a04...`) or re-upload.

## Note on perceived slowness
Two contributors: (a) the 15-min maintenance cron re-running `recover()` on the failed book, each attempt making many failing storage calls; (b) the Super Admin UI polling `/api/admin/master/*` very frequently (several calls/sec). Neither is a pod-resource problem; the hard failure is the storage 500.
