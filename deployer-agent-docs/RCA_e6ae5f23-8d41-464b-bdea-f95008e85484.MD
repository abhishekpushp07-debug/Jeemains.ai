## Answer: YES — a code-only redeploy is safe for live data and secrets

1. **DB is NOT cloned/replaced on redeploy.** The preview→prod data migration lives ONLY in the `provision_mongo` step, and that step runs data migration exclusively for `type='initial'` runs. This deployment already exists and every subsequent deploy is a `redeploy`, which SKIPS migration entirely. Your preview DB will not be copied over prod; the 144/53/1/14 live records are untouched by the pipeline. Only your importer's own insert-only writes change data.

2. **Mongo binding is preserved and always points at the same prod DB.** `MONGO_URL` and `DB_NAME` are platform SYSTEM keys regenerated from production state on every deploy — they always re-resolve to the SAME existing Atlas DB (`campus-search-debug-test_database`). The importer running in the prod pod will read/write exactly this live DB. No rebind, no new DB.

3. **Production secrets are preserved.** On every deploy after the first, custom/user secrets carry forward from the previous PRODUCTION run; any value the user set wins, and the preview `.env` can only ADD brand-new keys — it can never overwrite an existing prod secret. So ADMIN_EMAIL/ADMIN_PASSWORD/JWT_SECRET/EMERGENT_LLM_KEY/CORS_ORIGINS/FRONTEND_URL persist unchanged; SYSTEM keys are regenerated but resolve to the same resources. No secret edit is needed (and the deployer cannot change secrets anyway).

4. **Storage identity for the private PDFs.** The prod storage/integration binding the app uses to read existing private files is held in the prod environment (INTEGRATION_PROXY_URL and carried-forward secrets) and persists unchanged across a redeploy — so the importer will read the SAME private storage identity it reads today. The deployer cannot read the raw storage bytes, so byte-level hash identity is NOT verified here; that is correctly enforced by your importer's own fail-closed hash check at runtime. Keep that fail-closed behavior.

## The ONE mode caveat to confirm before deploying
The guarantees above hold for a normal **Redeploy** of this existing deployment. They would NOT apply to a **Replace** (the fork-style first deploy that builds a brand-new app + new DB alongside). This deployment's history is all redeploy, so a standard deploy-from-E1 will be a redeploy — just make sure the importer is shipped as a redeploy of `campus-search-debug`, not as a fork/replace into a fresh deployment.
