## Phase 3 — load test of OUR server (website replaced by tools/fake_website.py, 60 ms per call; 2 workers; 4-core container)
Tools: tools/fake_website.py, tools/loadtest_mock.py (--kind answer|attempt|asset|storm, --cleanup), tools/proto_proxy.py (benchmark-only aiohttp copy of the proxy).
| test | current proxy (httpx) | prototype (aiohttp) |
|---|---|---|
| answer saves, 50 users | 682/s, 727 req per CPU-s, p50 63 ms | – |
| answer saves, 800 users | 372/s, 188 req per CPU-s, p50 1.4 s, p99 8.2 s | 2,661/s, 1,263 req per CPU-s, p50 192 ms |

- L1 CRITICAL: proxy CPU per request grows with load (profile: ~25% of CPU inside the httpx/httpcore connection-pool bookkeeping). Fix: aiohttp upstream client (6.7x measured).
- L2 HIGH: a log line for every proxied request (httpx INFO) — CPU and log volume at 20k req/s.
- L3 HIGH: the student's IP is not passed to the website (no X-Forwarded-For) → the website sees all students as one IP; its limiter already blocked QA sign-ins ("wait 140 s" after ~9 logins; session checks 429 after ~7 in 5 min).
- L4 HIGH: on that 429 a reload signs the student out with "Connect to the internet", no retry (src/auth.tsx:58).
- L5 MEDIUM: PDF export costs ~43 ms CPU each (23 per CPU-s) — a post-mock PDF rush needs a queue/limit.
- Fine: Rank estimate 1,573 req per CPU-s; Rapid Fire ~2,900 players per core (memory/SCALE.md).
### Sizing for 1 lakh in one mock (our server only, AFTER L1-L3 + M1 CDN images + M2 spread)
- Steady ~1,500 req/s (saves + visits), start burst 2-5k req/s, 00:00 with spread ~10k small req/s for ~10 s.
- ~1,200 req per CPU-s → 10-15 busy cores → plan 32-40 cores (8-10 servers × 4 cores, 4 workers each) + MongoDB 4-8 cores.
- WITHOUT fixes: images alone ≈ 20 Gbps for ~5 minutes and the 00:00 storm ≈ 20k req/s × 58 KB — not reachable at any sensible size.
- Production capacity (number of servers, DB size) must be arranged with Emergent support; the preview runs 1 worker.

## Database integrity audit (our MongoDB; academic attempts/answers/results live in the website's database)
Structure: 28 collections. rf_profiles (uid unique; pid, friend_code unique partial) is the hub; rf_duels / rf_cups / rf_challenges /
rf_gangs / rf_friends (uid+fid unique) / rf_feed / rf_notices refer to it by uid strings (no foreign keys, no cascade).
Idempotency keys: rf_awards (uid+ref unique), rf_sessions (user_id+request_id unique), rf_learning_events (uid+ref unique),
mission_visits (code+key unique). Session plumbing: jl_jars (sid unique, no expiry), jl_locks (TTL), rf_access (TTL), rf_watch (TTL), rf_events (capped).
Checked read-only on the preview DB (production not inspected): no negative coins/diamonds/freezes, coins all integers, no duplicate phone_hash, no duplicate gang reports.
### Confirmed (code evidence)
- DB1 HIGH double reward / lost counts: gamify.award reads the profile, then `$set`s the whole day_stats / week_stats / streak / win_run from that old copy (gamify.py:168-199). A quest claim (371-372) or Diamond Rush chest (334-335) made in between is erased from day_stats.claimed / rush → the same quest/chest can be claimed again; two matches ending together lose Diamond-Rush gems and Friends-League XP.
- DB2 MEDIUM partial success: award marker is written first, reward after (gamify.py:136-144); a crash in between → replay returns {} → that match's coins/XP lost.
- DB3 MEDIUM partial payout: cups.finish flips status then pays each player in a loop (cups.py:163-176); a crash mid-loop leaves winners unpaid, nothing retries.
- DB4 MEDIUM lost cookie update: jl_jars save = read, merge, `$set` the whole cookie set (server.py:158-163); two servers receiving new cookies at once overwrite each other → random sign-outs at scale.
- DB5 MEDIUM jl_jars never expire, updated_at is text (cannot TTL): 670 rows here; grows with every device forever; old handles stay valid.
- DB6 LOW stuck rows: 10 duels "ready/waiting" > 2 h and 74 sprints "active" forever in preview (only closed when someone opens them).
- DB7 LOW orphans (preview): 63 award owners without profile, 2 friend rows without profile, 2 sprints of unknown users, 327/347 profiles are TEST leftovers.
- DB8 LOW rf_gang_reports has no unique (gang_id, uid) index → simultaneous reports can duplicate.
- DB9 MEDIUM (scale): every server process on start creates ~60 indexes, runs 2 update_many on rf_cards and upserts all ~14k cards + migrations; 40 processes deploying together = ~560k upserts at once.
### Risks / notes
- Mission "helped" counter is two steps (visit row, then +1): a crash in between undercounts by one.
- Time is stored three ways (float seconds, ISO text, datetime) — consistent per collection; TTL only works on datetime fields.
- No money values (coins/diamonds are integers). Buys, squads, chests, joins use guarded atomic updates (good).
- No migration framework: schema changes live in startup code; leftover backend/redis.supervisor.conf.
